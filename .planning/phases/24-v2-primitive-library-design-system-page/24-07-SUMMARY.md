## Parse Approach: Dual OKLCH/RGB Handler (Test 10 Deviation)

**Discovery:** The plan assumed Chromium would convert OKLCH to `rgb(r, g, b)` before returning from `getComputedStyle.color`. Modern Chromium (v105+) with OKLCH color space support returns the OKLCH value directly: `oklch(0.5 0.22 27)`.

**Fix applied (Rule 1 - Bug):** Test 10 branches on color format:
- **OKLCH path:** Parses `oklch(L C H)` → asserts H < 60° (red range), chroma > 0.1 (not neutral), and `errorColor` does NOT match `264.6` or `0.044` (body-text OKLCH fingerprint).
- **RGB path:** Parses `rgb(r, g, b)` → asserts R > G, R > B, R >= 120, and `errorColor !== 'rgb(20, 31, 57)'` (broken-state deterministic value).

The dual-path approach maintains the regression guard semantics regardless of Chromium version.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Test 10 required dual OKLCH/RGB color format parser**

- **Found during:** Task 6 first test run (g was undefined — channels parse failed)
- **Issue:** Modern Chromium (v105+) preserves OKLCH format in `getComputedStyle.color` — returns `oklch(0.5 0.22 27)` instead of converting to `rgb(r, g, b)`. The plan's test code assumed RGB output with `rgb(r, g, b)` parsing via comma-split.
- **Fix:** Added an `if (errorColor.startsWith('oklch(...'))` branch that parses `oklch(L C H)` and asserts H in red range (0-60°) plus chroma > 0.1 plus a body-navy fingerprint guard. The original RGB path is preserved as the else branch for legacy Chromium.
- **Files modified:** `tests/accessibility/v2-primitives.spec.ts`
