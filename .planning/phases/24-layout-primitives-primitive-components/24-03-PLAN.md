<objective>
Build TWO primitive components inside `_Components / Primitives`:
- **`Primitive / Input`** per COMP-02 — label + control + helper text + error slot composition. Variant cells: `Default`, `Focus` (D-22 forward for Phase 27 keyboard nav), `Error` (D-22 forward for Phase 27 contact form validation).
- **`Primitive / Badge`** per COMP-03 — shape and variant axis driven by D-32 (radius probe) + D-34 (kind probe) outcomes. May reuse existing `radius-semantic-button` OR extend the token surface with `radius-primitive-pill` + `radius-semantic-badge` per D-33 open-token-extension policy.

**Probe-first discipline applies to Badge** (RESEARCH Pitfalls 4 + 7):
- **D-32 Badge radius probe:** `batch_get` Crito hero badges + project-card metric badges; enumerate actual `cornerRadius` values. Pause for user on outcome (token-extension decision is consequential — Pitfall 7 prevention).
- **D-34 Badge kind probe:** Compare hero badges vs project-card metric badges structurally. Decide single-Badge-component (identical) vs two-variant `kind` axis (distinct).

For Input, no probe needed: COMP-02 dictates the children (label + control + helper + error slot); literal payload values come from PEN-INVENTORY § Tokens Written.

Every literal value in payloads has a binding row in PEN-INVENTORY.md `## Variant Evidence (Phase 24)` per OPEN-23-13 dual-track. Any new token from D-32 probe gets a row in `## Token Extensions (Phase 24)` with rationale answering "Does any other primitive need this token?" (Pitfall 7 prevention).

**Purpose:** Establishes Input as the compositional foundation for Phase 27's contact form (8 fields). Badge resolution lets Phase 25 Section/Header (if needed) and Phase 27 Compound/Card (project cards have metric badges per PEN-INVENTORY) instance the right kind.

**Output:** Input + Badge variant cells in `_Components / Primitives`, audit-trail rows for both, conditional Token Extension rows for Badge, probe outcomes documented.
</objective>
